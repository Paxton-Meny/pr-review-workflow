Settings reference

What each setting changes

Fifteen settings, grouped by what you are trying to control. Each entry says what the setting does in plain terms, lets you switch between its values to see what would differ on a pull request, and says when each value is the right one. Open the dialog with /plugin configure pr-review-workflow.

Merging

Auto-approve

KEY
auto_approve
DEFAULT
off
ACCEPTS
on | off

When a run finishes with nothing left open, the pull request is ready to merge. This setting decides whether the plugin merges it or asks you first.

If you set it to
review loop: 0 open, 5 verified
Everything holds. Merge now, or hold?
Merge nowHold
merge-pr: acme/api#128 merged

You are asked at the end of every clean run. When nobody is there to answer, the plugin posts a comment saying the review converged and stops; it never merges unattended with this off.

The pull request merges as soon as the loop is clean, whether or not anyone is watching.

Either way, nothing merges while a finding is open, or over a finding marked won’t-fix that you have not accepted.

Choose it when
off DEFAULT
Most projects. You keep the last word on every merge.
on
Repositories where a clean review is all you require, or unattended runs that should finish the job.

Works with · Check command

Proof and checks

Check command

KEY
check_command
DEFAULT
empty
ACCEPTS
a shell command

The command your project already uses to check itself: its test suite, or tests plus lint. The plugin runs it inside its own copy of the pull request, never in your checkout, and three behaviours depend on it.

For example, set it to
Suggested changes are proven
A suggestion posts once it applies cleanly to the file. Nothing is run.
A suggestion posts only if the check still passes with it applied. One that fails is withdrawn, and its finding posts without it.
Every round of fixes is gated
No gate. Fixes go straight to verification.
After each round of fixes the check must still pass. A failure gets one repair attempt; a second failure parks the run.
Check lines can execute
A finding’s Check line runs only if it starts with a contract command prefix.
A finding’s Check line runs when it starts with this command, such as npm test -- retry.

If the check already fails before any fix is made, the gate switches itself off for that run and the failure is handed to the reviewer as evidence.

This executes the pull request’s code on your machine. Read the security notes before pointing it at pull requests you do not trust.

Choose it when
empty DEFAULT
Projects with no single check command, or pull requests you do not want executed locally.
a command
Any project with a reliable test command. It is what turns a review opinion into a proof.

Works with · Contract command prefixes, Auto-approve

Contract command prefixes

KEY
contract_commands
DEFAULT
empty
ACCEPTS
command prefixes, separated by commas

A finding can carry a Check line: one command that proves the fix, such as a single test. The verifier runs that line instead of judging the fix by reading, but only when the line starts with a command you have approved. The check command is always approved; this setting approves more.

For example, set it to
Check: make check
Runs. It is the check command itself, in this example make check.
Check: go test ./retry -run TestExhausted
Not run: no approved prefix matches. The verifier judges the fix by reading instead.
Runs. The line starts with go test.
Check: go test ./... | tee out.txt
Never runs. A line containing a shell operator is refused, whatever is listed.

Separate prefixes with commas, not spaces, so that go test stays one prefix.

List test runners only. A bare interpreter such as python or sh as a prefix would let a Check line run anything.

Choose it when
empty DEFAULT
Your check command already covers every test you would want run on its own.
prefixes
Your check command is a wrapper such as make check, but single tests run through another tool.

Works with · Check command, Verifier model

Local standards files

KEY
local_standards
DEFAULT
empty
ACCEPTS
file patterns, separated by spaces

Some projects keep their rules in files that are not committed: a standards document, a team checklist. Name those files here and every review applies them. Their substance shapes the findings; their file names and wording never appear on the pull request.

A pattern is a path relative to your clone. A * stands for any run of characters in a file name, so docs/rules/*.md matches every Markdown file in that folder.

For example, set it to
Nothing project-specific is read from untracked files. Reviews follow the rules the repository states in tracked files, then the conventions visible in its code, then general practice.
On the pull request
F004best-practices · minor
Public function fetch() has no type annotations
Public functions in this project carry type annotations; this one has none.
Never on the pull request
Violates STANDARDS.md, section 3.
The rule is enforced; the file is not named or quoted.

Rules about commit messages and branch names are out of scope: the loop cannot rewrite history that is already pushed.

Choose it when
empty DEFAULT
Projects whose rules all live in tracked files, or that have none written down.
patterns
You keep private or uncommitted standards and want every review to hold changes to them.

Review depth

Second review pass

KEY
double_review
DEFAULT
risky
ACCEPTS
off | risky | always

After the first review, a second reviewer can read the same change again, looking only for what the first one missed. That second read is the gap pass. This setting decides when it happens on a change small enough for one reviewer.

If you set it to
A small, clean change
One reviewer. No risk signal fired.
Gap pass runs
No gap pass
A CI workflow change
One reviewer. The automation probe fired.
Gap pass runs
No gap pass
A change over 1,500 lines
Split into shards, one reviewer each.
Gap pass runs

A single-reviewer change never gets the second read. Cheapest; a miss waits for a human reviewer.

The second read happens only when a scripted check flags something that looks like a secret, or a change to automation such as a CI workflow.

Every change gets the second read, at roughly double the cost of the first review.

A sharded change always ends with a gap pass, whatever this is set to: each reviewer saw only part of it, so nothing else can catch a defect that spans two parts.

Choose it when
off
Throwaway or docs-heavy repositories, where a missed defect is cheap.
risky DEFAULT
Most projects. You pay for the second read only where a miss would hurt.
always
Code where a missed defect is expensive: payments, authentication, infrastructure.

Works with · Review samples, Strong model

Sensitive paths

KEY
sensitive_paths
DEFAULT
empty
ACCEPTS
file patterns, separated by spaces

Name the parts of the repository where a defect costs most: authentication, payments, database migrations. A change that touches one is treated as high stakes, even when nothing in the changed lines looks risky to the probes.

For example, set it to

A pull request changes one line in src/auth/session.py, with no keyword the probes look for.

The reviewer may climb
Routed on size and probes alone: the reviewer model.
Treated like a sensitive surface: the strong model, when one is set.
No fix there starts cheap
A minor finding with a proven suggestion may start on the cheap model.
Every fix in the file starts on the editor model at least, whatever the cost posture.
The second review pass runs
Under the risky setting, only when the probes flag a secret or a CI change.
Under the risky setting, a declared path counts as a risk signal.

A * matches any run of characters, slashes included, so src/auth/** and src/auth/* both cover everything under that folder. A project’s shared settings file adds its patterns to yours; it never removes them.

Choose it when
empty DEFAULT
The probes’ keyword checks are enough, or nothing in the repository is riskier than the rest.
patterns
Some directories hold code where a missed defect is expensive and whose changes do not always look dangerous line by line.

Works with · Second review pass, Strong model, Cost posture

Before anything is posted, a cheap second reader opens the code each finding points at and asks one question: does the code really show this? Findings that hold up post as inline comments. Findings it cannot support still post, but in the round’s summary comment, with the reason.

If you set it to

Choose it when

Models and cost

Models and cost

Five settings decide which model does which job. Three name a model for a role. One decides whether the plugin may swap those models when the change makes that safe or necessary. One names the stronger model it may climb to.

A model for each role

Reviewer model
reviewer_model default inherit

Runs the first, thorough review: the pass that finds the defects and writes their contracts.

Accepts · inherit (the model your session is using) or a model name such as sonnet or opus

Relates to · It is the floor for the gap pass. With no strong model set, it is also the highest routing can go.

Editor model
editor_model default inherit

Runs the agent that edits the branch, one commit per finding.

Accepts · inherit or a model name

Relates to · Routing can lower it for one narrow case, shown below. Nothing raises it.

Verifier model
verifier_model default sonnet

Runs the agent that checks each fix against its contract, and the precision filter’s re-read. Both are narrow questions with a yes or no answer, which is why the default is a cheaper model.

Accepts · inherit or a model name

Relates to · Routing never changes it. It is the only model setting whose default is not your session’s model.

Routing decides per unit of work, not per pull request: a sharded review is judged group by group on each group’s own files, and a first editing round splits into a mechanical batch and the rest when each holds at least two findings. The gap pass takes the highest rung any group used.

Each role also runs at a fixed reasoning effort set in its agent definition, whatever your session’s level: the reviewer and the arbiter high, the editor medium, the verifier and the filter low. Finding defects is where thinking pays; checking a fix against a stated contract is a narrow question.

Whether those choices can be overridden

Model routing
model_routing default auto

auto lets the plugin pick a cheaper model where the work is provably mechanical and a stronger one where the change is large or sensitive. fixed turns that off: every role runs on exactly the model its setting names.

Accepts · auto or fixed

Relates to · Reads the three role settings as its starting point and the strong model as its ceiling.

Strong model
strong_model default empty

The model auto routing climbs to for changes with over 800 changed lines of code (tests and docs not counted), for changes that touch concurrency, cryptography, authentication or injection surfaces, and for the one arbitration pass before a run parks.

Accepts · empty, or a model name such as opus

Relates to · Does nothing when routing is fixed. Left empty, climbing stops at the reviewer model.

Cost posture

KEY
cost_posture
DEFAULT
balanced
ACCEPTS
quality | balanced | economy

When a round of fixes begins, each open finding starts on a rung of the ladder. This setting decides how readily a fix may start on the cheap model. It only moves the starting rung: a fix that fails climbs one rung whatever the posture, and some findings never start cheap at all.

If you set it to
F001antipatterns · nit
Unused import left behind
Carries a proven suggestion: mechanical.
sonnetsonnetsonnet
F002correctness · major
Retry loop drops the final attempt’s error
Carries a Check line that will execute, so a wrong fix is caught by running it.
editor modelsonnetsonnet
F003best-practices · major
Timeout is read from the wrong config key
No Check line; only the check gate and the verifier stand behind it.
editor modeleditor modelsonnet
F004security · major
Token compared with a non-constant-time equality
A security finding never starts cheap, nor does a blocker or a file the secrets or sensitive probe flagged.
editor modeleditor modeleditor model

Only a fix with a proven suggestion starts on the cheap model. Everything else starts on the editor model.

A fix also starts cheap when its Check line will execute: the fix is proven by running it, so a cheap attempt costs at most one extra round.

Any fix starts cheap once a check command gates the round. The gate catches what breaks and the verifier catches what is not fixed; the bill is lowest and reopens are likeliest.

Shown with a check command set. Without one, there is nothing to catch a wrong cheap fix, so quality and balanced behave the same and economy adds nothing. The editor model is editor_model, by default your session’s.

Choose it when
quality
Correctness matters more than the model bill, or the project has no check command yet.
balanced DEFAULT
Most projects with a check command. Cheap where a wrong fix is caught by execution, your model everywhere else.
economy
A check command you trust to catch a wrong fix, and a bill you want down; expect the occasional extra round.

Works with · Check command, Contract command prefixes, Model routing

Housekeeping

Ledgers kept

KEY
keep_ledgers
DEFAULT
20
ACCEPTS
a whole number, 1 or more

Each reviewed pull request leaves a ledger on your machine: its findings, their notes, and how each one ended. After every merge the plugin tidies up, keeping the most recent ledgers for that repository as your audit record and deleting older ones.

For example, set it to
Kept
The 5 most recently finished ledgers for the repository that just merged.
The 20 most recently finished ledgers for the repository that just merged.
The 100 most recently finished ledgers for the repository that just merged.
Deleted
Finished ledgers of that repository older than those.
Never touched
A run that still has its working copy, because it is paused or parked and can resume. Ledgers of other repositories. The statistics file that records one line per finished run.

List what is on disk at any time with /pr-review-workflow:status.

Choose it when
lower
Disk space matters more to you than history.
20 DEFAULT
Most projects.
higher
You want a long audit trail, or more past runs to learn from.

Reference

Glossary

gap pass
A second review that reads the first one’s findings and reports only what they missed.
shard
One slice of a large change, read by its own reviewer in parallel with the others.
probe
A scripted pattern check over the change, run before any model, that flags things like possible secrets or CI edits.
contract
The Resolution line on a finding: the testable statement a fix must make true.
Check line
An optional line on a finding naming one command, usually a single test, that proves the fix.
suggestion
A ready-to-commit replacement posted with a finding, which you can apply from the pull request page.
ledger
The per-pull-request directory on disk that holds the findings and the round count.
round
One pass of fixing and verifying. A run has at most four.
park
To stop a run that is not converging, leaving a status comment and everything needed to resume.
arbitration
One extra verification pass on a stronger model, used when a finding keeps being reopened.
